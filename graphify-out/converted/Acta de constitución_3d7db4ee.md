# Descripción del proyecto
## Objetivos del Negocio
| Construcción de un Aplicativo informático que ayude al usuario en caso de diferentes emergencias entregando información a sus contactos de emergencia: Urbano Emergencia Médico Adulto Mayor |
| --- |
## Justificación del proyecto – Contexto
| Al percatarse de diferentes tipos de incidentes a personas de riesgo, nos fijamos de que no tienen alguna herramienta que cumpla las necesidades del usuario para obtener un socorro efectivo tanto de un personal médico o un contacto de emergencia que este tenga. Al comparar el contexto con otras aplicaciones, estas cumplen con algunas de las áreas de interés pero, a su vez, no las unifica en 1 sola para así poder tener todas esas funciones en la palma de la mano. |
| --- |
## Problema-Necesidad
| Cuando ocurre alguna emergencia, ya sea un robo, emergencia médica o accidente, buscamos que la persona afectada se pueda comunicar con su red de seguridad más cercana, enviando información relevante del contexto del usuario, a su vez con la ubicación de donde se generó la alerta, debido a que en casos de hurtos obtener la información a tiempo real del dispositivo puede ser contraproducente para la ayuda del usuario. Con esa información, le da la opción a los números vinculados del usuario auxiliarlo de forma más rápida, obteniendo información médica relevante la cual ayudaría al personal médico de ser necesario, y la tenencia de un historial del incidente esta le podría ayudar a facilitar procesos legales o de reposición de documentación que llegase a necesitar. |
| --- |

# Descripción del producto
## Solución Propuesta
| Construcción de un Aplicativo informático que ayude al usuario en caso de diferentes emergencias entregando información a sus contactos de emergencia: Urbano: Enviar ubicación del afectado y un mensaje personalizado creado por el usuario. Emergencia: Enviar ubicación del afectado y un mensaje personalizado creado por el usuario. Médico: enviar ubicación del afectado, un mensaje personalizado creado por el usuario y un mensaje con la información médica relevante del usuario. Adulto Mayor: enviar ubicación del afectado, un mensaje personalizado creado por el usuario, un mensaje con la información médica relevante del usuario y configuración de la aplicación móvil reducida. |

# Descripción del sistema
## Requerimientos de alto nivel
| Módulo Usuario: RF1: El sistema debe permitir crear una cuenta al usuario RF2: El sistema debe permitir iniciar sesión al usuario con sus credenciales RF3: El sistema debe poder modificar las credenciales de los usuarios y personal de soporte desde la página web / escritorio / móvil RF4: El sistema debe permitir al usuario modificar las especificaciones y finalidades del mismo según su tipo de emergencia (Urbano, Medico, Emergencias y Adulto mayor) RF5: El sistema debe permitir al usuario configurar el método de activación del SOS según su tipo de usuario. Para personas mayores o usuarios con acceso limitado, la configuración predeterminada requiere mantener pulsado el botón SOS durante 5 segundos. La activación con la aplicación en segundo plano o cerrada (acceso directo, widget o botón físico) se implementará solo donde el sistema operativo lo permita sin código nativo adicional y se clasifica como Could Have (prioridad pendiente de confirmación). El valor para el resto de perfiles queda pendiente de confirmar. RF6: El sistema debe tener al menos 1 contacto de emergencia ingresado dentro de un usuario/cuenta para su correcto uso. RF7: El sistema debe tener un máximo de 5 contactos de emergencia por usuario: la cuenta principal y cada usuario apadrinado deben poder administrar su límite de 5 contactos RF8: El sistema debe tener un máximo de 5 usuarios apadrinados posibles dentro de una cuenta RF9: El sistema debe tener los datos personales filtrados para cada cuenta y sus usuarios apadrinados RF10: El sistema debe poder filtrar información médica y que está solo sea compartida a las personas designadas por el usuario. Módulo Alertas: RF11: El sistema debe enviar un mensaje a los contactos de emergencia registrados por el usuario RF12: El sistema debe enviar un mensaje personalizado dependiendo de la finalidad del usuario (Urbano, Medico, Emergencias y Adulto mayor) RF13: El sistema debe compartir la última ubicación ingresada desde el dispositivo a los contactos de emergencia del usuario. RF14: El sistema debe mostrar al usuario los números oficiales de emergencia (131, 132 y 133) Sistema en General: RF15: Se debe tener una aplicación de escritorio la cual administre el software. RF16: La aplicación web debe realizar ventas de planes de cuenta de usuario y de cupos para usuarios apadrinados, utilizando PayPal en modo sandbox (pruebas) y Mindicador para la conversión CLP–USD. RF17: El sistema debe generar descuentos a usuarios que quisieran apadrinar otra cuenta dentro de ella. RF18: La aplicación web debe poder realizar contacto de soporte en caso de problemas de software de los usuarios. RF19: La aplicación de escritorio debe poder gestionar las cuentas vinculadas a los usuarios, sin perder el espacio apadrinado anteriormente. RF20: La aplicación de escritorio debe permitir al usuario con rol ADMINISTRADOR, consultar y modificar los datos del sistema exclusivamente a través de los datos expuestos por la API del backend RF21: La aplicación de escritorio debe poder generar informes de seguimiento de los usuarios. RF22: La aplicación web y móvil deben poder generar informes de seguimiento personales de las cuentas. RF23: La aplicación web y móvil debe funcionar con un sistema de pin único que esté vinculado a la cuenta principal para el ingreso personal de los usuarios. RF24: La aplicación web y móvil el primer inicio de sesión debe estar vinculado a la cuenta principal. RF25: La aplicación web y móvil debe permitir al usuario principal definir sus usuarios apadrinados y el nivel de acceso de cada uno (acceso completo o parcial), y solicitar asistencia al personal de soporte en caso de ayuda para gestionarlo |

# Requisitos de aprobación del proyecto
| RNF1: Las aplicaciones deben ser responsivas RNF2: La aplicación web debe ser compatibles entre navegadores RNF3: El sistema debe garantizar la seguridad al gestionar correos y credenciales de ingreso RNF4: El backend debe ser el único encargado de procesar la seguridad mediante un modelo estricto de control de acceso basado en roles con catálogo cerrado (administrador, soporte, usuario). El usuario se subclasifica en principal o apadrinado según su vínculo. Al igual que se considera una verificación de propiedad de recursos en cada endpoint que reciba un identificador en torno al usuario. RNF5: El sistema debe garantizar la seguridad y confidencialidad de los datos proporcionados por el usuario RNF6: Al momento de emergencia, el sistema debe registrar la alerta e iniciar acción en un máximo de 3 segundos, y el primer intento de despacho a cada contacto en un máximo de 10 segundos desde la alerta. RNF7: El sistema debe garantizar la persistencia de las alertas ante fallos, y mantener una disponibilidad objetivo del 99% mensual RNF8: El sistema debe proteger los datos de salud conforme a la Ley 21.719, exigiendo consentimiento explícito, aplicando cifrado y limitando el acceso a la ficha médica sólo durante emergencias activas RNF9: Al eliminar una cuenta, el sistema debe suprimir la información personal y médica de forma inmediata, conservando únicamente el historial de alertas para fines de auditoría/legales RNF10: Las interfaces de activación SOS y configuración de contactos deben cumplir con el estándar de accesibilidad WCAG 2.1 nivel AA |
